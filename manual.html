AIエージェント・ワークフロー
使い方手順書（コーダー向け）

Figma → Claude Code → 静的HTML のループを、初期セットアップから月次レビューまで通しで実行するための手順書です。

対象 フロントエンジニア・コーダー
前提 macOS / Linux 環境、ターミナル操作の基本
所要 初回セットアップ 約30分

概要 — このワークフローの全体像

あなた（コーダー）が触る部分の流れを最初に把握しましょう。

3つのフェーズ

① 初期セットアップ：このワークフローを使い始めるときに1回だけ行う作業です。Node.js環境、Figmaトークン、リポジトリ取得、Playwright インストールなどが含まれます。所要時間 約30分。

② 案件ごとの実行：新しい案件が始まるたびに行う作業です。Figma構造チェック → 中間仕様生成 → Visual Diffループ → 振り返り、という流れで進めます。所要時間は案件規模次第。

③ 月次レビュー：月に1回、または案件3件溜まった時点で行う振り返り会です。ダッシュボード確認、ルール更新提案レビュー、チームへの共有が含まれます。所要時間 約30分。

ワークフロー全体図

💡 ポイント：あなたが「実行」「補完」する部分と、Claude Code が「自走」する部分がはっきり分かれています。AI に任せられるところは任せ、人にしかできない部分（仕様の補完、最終確認、コーダー追記）に集中しましょう。

① 初期セットアップ（1回だけ）

最初に1回だけ行う環境構築の手順です。所要 約30分。

事前準備チェックリスト

  • macOS または Linux（WSLでも可）
  • Node.js 20以上 がインストール済み（node -v で確認）
  • git が使える環境
  • Claude Code がインストール済み
  • Figma アカウントを持っている
  • Figma Desktop App がインストール済み（ブラウザ版だけでは MCP が使えない）
  • Figma の Professional プラン以上（Dev Mode が含まれる）

Step 1: 社内Gitリポジトリをクローン

このワークフロー用のリポジトリを取得します。社内Gitに ai-coding-workflow として登録されている想定です。

$ git clone https://git.your-company.internal/web/ai-coding-workflow.git
$ cd ai-coding-workflow

Step 2: Node.js依存関係をインストール

Visual Diff ループで使う pixelmatch, playwright, pngjs をインストールします。

$ cd visual-diff-loop
$ npm install
$ npx playwright install chromium
注意：Playwright の Chromium ダウンロードは約100MBあります。社内プロキシ環境の場合は HTTPS_PROXY 環境変数を設定してください。

Step 3: Figma個人アクセストークンを取得

Figma にログイン → 右上のアイコン → Settings → Personal access tokens → "Generate new token" でトークンを作成。スコープは "File content" 読み取りが最低限必要です。

取得したトークンを安全な場所に保管します。~/.zshrc や ~/.bashrc に追記する例：

# ~/.zshrc などに追記
export FIGMA_TOKEN="figd_xxxxxxxxxxxxxxxxxxxxx"

反映するには source ~/.zshrc またはターミナル再起動。

セキュリティ：このトークンは Figma の全ファイルにアクセス可能です。絶対にGitにコミットしないでください。.gitignore に .env が含まれていることを確認。

Step 4: Claude Code が Skill を認識できるか確認

このリポジトリの skills/ 配下を、Claude Code が認識できるパスに配置するか、シンボリックリンクします。

# 例: ~/.claude/skills/ にリンク
$ ln -s "$(pwd)/skills/figma-structure-check" ~/.claude/skills/
$ ln -s "$(pwd)/skills/figma-to-spec" ~/.claude/skills/
$ ln -s "$(pwd)/skills/workflow-improvement" ~/.claude/skills/

Claude Code を起動して、Skill が見えるか確認：

$ claude
# Claude Code 内で:
> list_skills
# → figma-structure-check, figma-to-spec, workflow-improvement が表示されればOK

Step 5: Figma Dev Mode MCP Server を有効化（推奨）

Claude Code が Figma の構造を直接読み取れるようにします。これは「経路1: Figma MCP」に対応する設定で、無くてもワークフローは degrade モードで動きますが、設定すると再現率が安定し、AI とのやり取りもスムーズになります。

A. Figma Desktop App 側を ON にする
  1. Figma Desktop App を起動
  2. メニューから Figma → Preferences（macOS）または メニュー → Preferences（Windows）
  3. "Enable Dev Mode MCP Server" のトグルを ON にする
  4. 確認メッセージが出たら承認
  5. 「Server is running on http://127.0.0.1:3845」 のような表示が出れば成功
B. Claude Code 側に MCP サーバーを登録

コマンドラインで登録するのが手軽です：

$ claude mcp add figma --transport sse --url http://127.0.0.1:3845/sse

または、~/.claude/settings.json（グローバル）または
プロジェクトルートの .mcp.json に以下を直接記述：

{
  "mcpServers": {
    "figma": {
      "type": "sse",
      "url": "http://127.0.0.1:3845/sse"
    }
  }
}
C. 動作確認
  1. Figma Desktop App で適当なテスト用ファイルを開いておく
  2. 別ターミナルで Claude Code を起動
  3. Claude Code 内で次のように質問する： 
    > figma の MCP ツールは使えますか？利用可能なツール一覧を見せてください。
  4. get_code, get_image, get_variable_defs などのツール一覧が表示されればOK
注意：作業中は Figma Desktop App を起動しっぱなしにしてください。アプリを閉じると MCP サーバーも停止します。
💡 個人プランの場合：Dev Mode MCP は Professional 以上のプランに含まれます。個人プランの方は (1) Professional へアップグレード、(2) コミュニティ製の figma-developer-mcp を npm で導入、(3) MCP なしの degrade モードで運用、のいずれかを選択してください。

Step 6: 動作確認（任意）

サンプル Figma ファイルキーで動作確認します。サンプル用のFigmaキーは社内 Wiki /web/ai-coding-workflow/sample に掲載があります（想定）。

$ export FIGMA_FILE_KEY="sample_xxxxxxxx"
$ node skills/figma-structure-check/scripts/check-figma.js --report

レポートが出力され、Claude Code 内で Figma MCP ツールが見えていればセットアップ完了です。

✅ セットアップ完了！ 次は実際の案件で運用に入ります。「案件ごとの実行手順」セクションへ進んでください。

② 案件ごとの実行手順

新しい案件が始まるたびにこの流れを実行します。

案件開始時のチェックリスト

  • デザイナーから Figma URL を受領した
  • 案件名・業種・CMSが分かっている
  • ディレクターから WBS / 工期 を受領した
  • 顧客固有の業界制約（薬機法/WCAG等）の確認が済んでいる

Step 1: 案件ディレクトリを作成

案件ごとに独立したディレクトリを切ります。命名規約：yyyymm-案件slug

$ cd ~/projects/
$ cp -r ~/ai-coding-workflow/visual-diff-loop ./202605-osaka-koukou
$ cd 202605-osaka-koukou

Step 2: 環境変数に Figma ファイルキーを設定

Figma URL の /file/【ここ】/... 部分がファイルキーです。

$ export FIGMA_FILE_KEY="abc123XYZdef"
# FIGMA_TOKEN は .zshrc で設定済みのはず

Step 3: Figma構造チェック（必須・最初に行う）

デザインが「AIに渡せる状態」かを確認します。エラーが出たらコーディングに入らず、デザイナーへ差し戻します。

$ node ~/ai-coding-workflow/skills/figma-structure-check/scripts/check-figma.js --report > report/structure-check.md
# JSON形式も同時に出力（自動振り返りで使う）
$ node ~/ai-coding-workflow/skills/figma-structure-check/scripts/check-figma.js > report/structure-check.json
判定ルール：エラー（error）が1件でもあれば、デザイナーへ report/structure-check.md をそのまま送って差し戻し。警告（warning）のみなら次に進んで良いが、再現率が伸びない場合は警告も見直しの対象。

Step 4: 中間仕様 spec.md を生成（自動）

Figma構造から spec.md の叩き台を自動生成します。

$ node ~/ai-coding-workflow/skills/figma-to-spec/scripts/generate-spec.js \
    --project "○○高校コーポレートサイト" \
    --out ./docs/spec.md

標準エラー出力に「TODO残数」が表示されるので確認します。

Step 5: spec.md の [TODO] を埋める（あなたとディレクターの作業）

生成されたspec.mdをエディタで開き、[TODO] マーカーをすべて埋めます。

埋めるべき主な項目：

  • 顧客名、業種、ターゲット、業界制約
  • 公開URL、CMS種別
  • インタラクション仕様（Figma Prototypeでカバーされていないもの）
  • 検収基準（再現率閾値、Lighthouseスコア目標）
  • 再現困難パターン検出時の対応方針
💡 ディレクターと協働：顧客情報・業界制約はディレクターから情報をもらいながら埋めます。「Slack で確認 → spec.md に転記」のリズムで進めましょう。

Step 6: targets.json を編集して比較対象を指定

Visual Diff で比較する各セクションの Figma Node ID と、レンダリング先URLの対応を scripts/targets.json に記述します。

// scripts/targets.json
{
  "targets": [
    {
      "id": "hero",
      "label": "ヒーロー",
      "figmaNodeId": "1:23",
      "renderUrl": "http://localhost:3000/index.html#hero",
      "viewports": ["pc", "sp"],
      "threshold": 0.97
    }
  ]
}

Figma Node ID は、Figma上でセクションを選択 → 右上の「Share」→ URLの ?node-id=【ここ】 から取得できます。

Step 7: Claude Code を起動して Visual Diff ループを開始

案件ディレクトリで claude コマンドを起動。Claude Code はルートの CLAUDE.md を自動で読み、ループに入ります。

$ claude
# Claude Code 内で:
> docs/spec.md と targets.json を読み、Visual Diff ループを開始してください

あとは Claude Code が自走します。以下を繰り返します：

  1. npm run fetch-figma で正解画像取得
  2. src/ に静的HTML生成
  3. npx serve src -p 3000 でローカル起動
  4. npm run render でスクショ
  5. npm run diff で比較
  6. 閾値未満なら差分を読んで修正 → 2 に戻る
あなたの役割：基本は見守るだけ。Claude Code が判断に詰まったり、Figmaに再現不能な指定を見つけた時に質問してきます。

Step 8: 最終確認

Claude Code が「完了」と報告したら、生成された report/index.html をブラウザで開いて目視確認します。

$ open report/index.html

確認ポイント：

  • Figma / 生成 / 差分 の3カラムで全ターゲットが PASS している
  • 差分があってもピクセル単位の細かい差で本質的に問題ない
  • セマンティックHTMLが適切（<article>, <section>, 見出し階層）
  • レスポンシブが意図通り動く
  • WCAG 2.1 AAレベルのアクセシビリティが守られている

Step 9: 振り返り（retrospective.md）の作成

Claude Code が CLAUDE.md の指示に従って自動で retrospective.md を生成しているはずです。生成されていなければ手動で実行：

$ node ~/ai-coding-workflow/skills/workflow-improvement/scripts/generate-retrospective.js \
    --project "○○高校コーポレートサイト" \
    --diff-report ./report/diff.json \
    --spec ./docs/spec.md \
    --structure-check ./report/structure-check.json \
    --duration 47 \
    --iterations 3 \
    --out ./retrospectives/202605-osaka-koukou.md

生成された retrospectives/202605-osaka-koukou.md を開き、[CODER NOTE] セクションを 5〜10分で埋めます。

埋めるのは4つだけ：

  1. AI が捉えきれていない問題
  2. 再現率は出たが本質的には正しくない箇所
  3. デザイナーへ伝えたい改善要望
  4. このワークフローへの改善要望

Step 10: バックエンジニアへの引き継ぎ

静的HTMLが完成したら、バックエンドエンジニアに渡します。引き継ぎセットには以下を含めます：

  • src/ — 静的HTML/CSS/JS一式
  • docs/spec.md — 中間仕様（CMS可変領域の定義含む）
  • report/diff.json — 最終再現率レポート（参考）

共有Gitリポジトリにコミットしてプルリクを作成、またはZip化して共有フォルダへ。

Step 11: 中央リポジトリに retrospective をコミット

案件ディレクトリの retrospectives/ 配下のファイルを、社内ワークフロー用Gitリポジトリの retrospectives/ へコミットします。月次レビューで集計されます。

$ cp ./retrospectives/202605-osaka-koukou.md ~/ai-coding-workflow/retrospectives/
$ cd ~/ai-coding-workflow
$ git add retrospectives/202605-osaka-koukou.md
$ git commit -m "retro: ○○高校コーポレートサイト"
$ git push
✅ 案件完了！ お疲れさまでした。retrospective が蓄積されることで、次の案件でルールがより精緻化されていきます。

技術解説 — Figma の情報がどう流れるか

Step 7「Visual Diff ループ」の内部で、Claude Code が Figma の情報をどう扱っているかを解説します。深く理解しなくても運用はできますが、ループが詰まった時にここを知っていると判断が早くなります。

3つの経路で Figma の情報を扱う

「Figma → 静的HTML」と一言で言っても、実は性質の違う3種類のデータが流れています。これを混ぜると設計が破綻するので、経路を分けています。

3経路の比較表

項目 経路1: MCP 経路2: fetch-figma.js 経路3: アセット書き出し
目的 AI がデザイン構造を読む 比較用の正解画像を得る HTML に埋め込む素材を得る
タイミング コーディング中（毎回） セッション開始時（1回） 実装中（必要に応じて）
取得形式 JSON（ノードツリー、CSS候補） PNG（Frame 全体レンダリング） SVG / PNG（個別レイヤー）
保存先 AI コンテキスト（disk 不要） references/ src/images/ または インライン
使うもの Claude Code pixelmatch ブラウザ（最終ユーザー）
解像度 — 2x（比較用に高解像度） 1x or 2x（運用ポリシー次第）

アセット実装ルール（@img- などの判断ロジック）

Claude Code は CLAUDE.md に書かれたこのルールに従って、レイヤーごとに最適な実装方法を選びます。

Figmaレイヤーの種類 HTMLでの扱い 例
@img- かつ VECTOR インライン SVG として埋め込み <svg viewBox="..."><path d="..."/></svg>
@img- かつ IMAGE fill 外部画像として書き出し→参照 <img src="images/hero.png" alt="...">
グラデーション・シャドウ CSS で再現（画像化禁止） background: linear-gradient(...);
シンプルなアイコン 原則インライン SVG CSS で fill 変更可能にする
装飾文字（飾り絵文字等） SVG 化を検討、CSS擬似要素で代替可能 —
💡 インライン SVG を優先する理由：CSS から色やサイズを後で変更できる、HTTP リクエストが減る、ファイルサイズが小さい（小さい画像なら）、印刷時にも綺麗。一方でファイル本体に直接書かれるので、再利用するなら外部 SVG にする判断もアリ。

なぜ fetch-figma.js を Figma MCP に統合しなかったか

理論上は「Figma MCP だけで全部やる」設計も可能ですが、5つの理由で分離しています。

1. 決定論性 — 毎回同じ結果が必要

Visual Diff の比較は、毎回まったく同じ参照画像で行わないと再現率の数値が安定しません。MCP 経由だと、呼び出しタイミングや内部処理の揺らぎで微妙な差が出る可能性があります。ローカルキャッシュにすれば完全に安定します。

2. トークンコスト — 5回反復で大量消費

Visual Diff ループは最大5回反復します。毎回MCPで画像を引いていたらトークンを大量消費します。一度ローカルに置けば、追加コストはゼロです。

3. 責務分離 — pixel diff は決定論的処理

pixel diff は「決定論的・スクリプト的」処理であり、AI 推論を介在させるべきではありません。Claude Code が誤った判断をしても、diff 自体は常に同じ結果を返す状態が望ましい。

4. パイプライン互換性 — disk上のファイルが必要

pixelmatch も Playwright も「disk 上のファイル」を要求します。MCP のレスポンスをファイル化するより、最初から disk に置く方が自然です。

5. バージョン管理 — デザイン履歴のスナップショット

参照画像を references/ に置けば「いつデザインが変わったか」のスナップショットになります（任意で git にコミット可能）。差分の原因がデザイン変更にあるかを後追いできます。

Step 7 の内部動作（技術的分解）

手順書の Step 7「Visual Diff ループを開始」の中で、3つの経路がどう連携するかを順を追って示します。

[Claude Code 起動]
   │
   ├─ Read: CLAUDE.md / docs/spec.md / scripts/targets.json
   │
   ▼
[Figma MCP 接続]                                          ← 経路1
   AI: 「ヒーローセクションの構造を教えて」
   MCP: 「Frame "Hero", Auto Layout: vertical, padding: 96px...
         子要素:
           TEXT "title" (font-size: 36px, color: var(--color-primary))
           RECTANGLE "@img-hero-bg" (image fill)
           VECTOR "@img-arrow" (path: ...)」
   │
   ├─ 並行: npm run fetch-figma                        ← 経路2
   │   → references/pc/hero.png 取得（正解画像）
   │   → references/pc/feature.png 取得
   │
   ▼
[Claude Code がコード生成]
   - HTML/CSS は経路1（MCP の情報）から書く
   - @img-hero-bg → Figma Image API で書き出し          ← 経路3
     → src/images/hero-bg.png
     → HTML: <img src="images/hero-bg.png" alt="...">
   - @img-arrow → SVG として書き出し → インライン埋め込み ← 経路3
     → HTML: <svg viewBox="..."><path d="..."/></svg>
   - グラデーション → CSS の linear-gradient で再現
     （経路3 は使わない、画像化しない）
   │
   ▼
[npx serve src で起動 → render.js でスクショ取得]
   → renders/pc/hero.png（Playwright が生成）
   │
   ▼
[visual-diff.js 実行]                                       ← 経路2 を使う
   references/pc/hero.png ↔ renders/pc/hero.png
   pixelmatch で比較
   → report/diff.json にスコア記録
   │
   ▼
[Claude Code が diff.json を読む]
   pass: false → 差分画像を見て src/ を修正 → 上に戻る
   pass: true  → 完了 → retrospective 生成へ

運用中の落とし穴

この経路分離の理解が曖昧だと、次のような不具合が起きます。気づいたらここを疑ってください。

落とし穴1：経路2と経路3を取り違える
参照用 PNG をそのまま HTML に埋め込むと、ページが重くなる（高解像度すぎる）。逆に、HTML 埋め込み用の低解像度画像で Visual Diff を実行すると、常に偽の差分が出る。
落とし穴2：経路1（MCP）だけで実装しようとする
Claude Code が「Figma が見ている JSON」だけで実装すると、ピクセル単位の差を検出できない。経路2 が無いと比較できず、再現率の数値も出ない。
落とし穴3：経路3を CSS で済まそうとする
写真や複雑な装飾を CSS だけで再現しようとすると不可能で、再現率が頭打ちになる。素材として書き出すべきは書き出す。

Step 1: ダッシュボードを生成して全体傾向を把握

$ cd ~/ai-coding-workflow
$ node skills/workflow-improvement/scripts/dashboard.js \
    --retrospectives ./retrospectives/ \
    --out ./dashboard.html
$ open dashboard.html

確認ポイント：

  • 再現率の推移は上向きか、停滞か
  • 反復回数は減ってきているか
  • 苦戦パターンのランキング上位は何か

Step 2: ルール更新提案を生成

$ node skills/workflow-improvement/scripts/propose-rule-updates.js \
    --retrospectives ./retrospectives/ \
    --rules ./skills/figma-structure-check/rules/check-rules.json \
    --out ./rule-update-proposals/$(date +%Y%m).md

生成された rule-update-proposals/202605.md を開いて、提案内容を確認します。

Step 3: 提案を検討してルール反映するかを判断

提案された各項目について、以下のいずれかを選択：

  • 採用 — skills/figma-structure-check/rules/check-rules.json を直接編集して反映
  • 保留 — 今回はパス、次回もう一度判断
  • 却下 — このパターンは今後ルール化しない（理由を提案ファイルに追記）
必ず人がレビュー：AI 提案を盲信せず、必ず内容を読んで判断してから反映してください。誤った変更は全案件に影響します。

Step 4: 変更をコミットしてチームに共有

$ git add skills/figma-structure-check/rules/check-rules.json rule-update-proposals/
$ git commit -m "rules: 2026/05 月次更新 - background-blur 閾値見直し他"
$ git push

Slack等で「ルールが更新されました」とチームに通知し、簡単な変更点サマリーを共有。

トラブルシューティング

よくあるエラーと対処法。詰まったらここを最初に確認してください。

FIGMA_TOKEN や FIGMA_FILE_KEY が認識されない

echo $FIGMA_TOKEN で値が出るか確認。空ならシェル設定ファイル（~/.zshrc など）に export 文があるか、source されているか確認。新しいターミナルを開き直すのも有効です。

$ echo $FIGMA_TOKEN
# 何も出ないなら未設定
$ export FIGMA_TOKEN="figd_xxxxx"
$ echo $FIGMA_TOKEN
Figma API が 403 / 404 を返す

主な原因は3つ：

  • トークンの権限不足 — Figma設定でトークンの「File content」スコープを確認
  • ファイルキーが間違っている — URL の /file/【ここ】/ 部分を再確認
  • ファイルへのアクセス権がない — Figmaファイルが共有されているか確認。デザイナーに依頼
Playwright のスクショと Figma 書き出しのサイズが違う

scripts/render.js の deviceScaleFactor: 2 と、fetch-figma.js の scale=2 が揃っているか確認。違うスケールで比較すると差分が大きく出ます。

また、Figma側のFrameサイズと targets.json の viewports の値が大きくズレているとはみ出しが発生します。

Visual Diff スコアが上がらない（90%前後で頭打ち）

主な原因と対処：

  • フォント描画差 — Figmaとブラウザのアンチエイリアスが原因。3%以下なら諦め、それ以上なら letter-spacing / font-feature-settings で吸収を試みる
  • 強いブラー — backdrop-filter はブラウザ差大。代替案を spec.md に「再現困難パターン」として追記
  • レイアウト解釈差 — Auto Layout の gap と CSS の gap の解釈が違うことがある。padding/margin ベースに置き換えると安定
  • Figma側に問題 — 構造チェック Skill を再実行。warning が大量に出ていれば、デザイナーに差し戻し
Claude Code が「完了」と言うのに、スコアが閾値未満

CLAUDE.md が正しく読まれていない可能性。Claude Code 内で以下を実行：

> CLAUDE.md を再度読んで、未達ターゲットがないか確認してください

それでも完了扱いするなら、上限反復回数（デフォルト5回）に達した可能性。targets.json の maxIterations を増やすか、該当ターゲットを再現困難パターンとして扱う方針に切り替えます。

retrospective.md の [AI が補完] が空のまま生成される

generate-retrospective.js はテンプレート埋めのみ行い、自然言語部分は Claude Code が後から書き加える設計です。CLAUDE.md に振り返り生成手順が記載されているか確認。手動で Claude Code に依頼するなら：

> retrospectives/202605-osaka-koukou.md を開き、[AI が補完] のセクションを埋めてください
npm install が遅い / 失敗する

社内プロキシ環境の場合、npm config set registry で社内ミラーを指定するか、~/.npmrc で proxy を設定。Playwright の Chromium DL は別途プロキシ設定が必要な場合があります。

export HTTPS_PROXY=http://proxy.your-company:port
export HTTP_PROXY=http://proxy.your-company:port
Figma MCP に繋がらない／ツールが表示されない

確認すべき項目を順番に：

  1. Figma Desktop App が起動しているか — ブラウザ版では MCP は動きません
  2. Dev Mode MCP Server が ON か — Figma Preferences で確認、トグルが ON になっているか
  3. ポート3845が使われていないか — lsof -i :3845 で確認。他のプロセスが占有していたら停止
  4. Claude Code 側の MCP 設定 — claude mcp list で figma が登録されているか確認
  5. プラン確認 — Dev Mode は Professional プラン以上に含まれる

それでも動かない場合は、MCP なしの degrade モードで運用できます。spec.md と references/ の画像だけで Claude Code はコーディングできます。再現率は若干落ちる可能性がありますが、ループは回ります。

Figma Desktop App を閉じたら Claude Code が止まった

Dev Mode MCP Server は Figma Desktop App のプロセス内で動いているため、アプリを閉じると停止します。作業中は Figma を起動しっぱなしにしてください。

うっかり閉じてしまった場合は、Figma を再起動して Dev Mode MCP が ON のままになっていることを確認 → Claude Code 内で MCP の再接続を促すと復帰します。

ダッシュボードが「集計対象 0 件」と表示される

retrospectives/ ディレクトリに .md ファイルが存在し、それぞれに正しい frontmatter（--- name: ... ---形式）が付いているか確認。frontmatter が壊れているファイルは集計対象外になります。
