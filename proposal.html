課題分析

部署内のAI活用は進んでいますが、部署間連携で再現率と工数のロスが発生しています。

営業 → 制作チーム

ヒアリング内容（顧客のニュアンスや背景）が制作側に伝わらない。受注時の見積と実作業の工数が乖離する。

本提案では別途扱う想定。

本提案の主題

デザイン → エンジニア

Figmaデザインを Claude Code に渡してコーディングする際に、「だいたい合っているが100%ではない」状態で生成が止まる。Figma側の作り方ルールが未整備のため、AIが構造を読み違える。

「だいたい合っている」が止まらない3つの原因

1. Figma側

Auto Layout未適用、Variables未使用、レイヤー名がデフォルトのまま等、AIが構造を解釈できないデザインが渡される。

2. 受け渡し側

Figma MCPで取れる情報には限界がある。インタラクション、複雑な効果、画像のベクター情報などが劣化する。

3. 生成側

AIには「正解と比較する目」がない。人が「ここが違う」と指摘するまで気づけず、再現率が頭打ち。

提案概要

3つの仕組みを直列に配置することで、上記の3原因をそれぞれ潰します。

3つの構成要素 — 詳細

各仕組みの目的、入出力、社内での使い方をタブで切り替えて確認できます。

figma-structure-check

目的：Figmaが「AIに渡せる状態」かを機械的にチェックし、デザイナーに修正リストを返す。

使う人：デザイナー（セルフチェック）／ディレクター（承認ゲート）。

チェック項目

  • Auto Layout の使用（FRAMEがすべてAuto Layout になっているか）
  • Variables または Color/Text Styles にバインドされた色・タイポ・spacing
  • 繰り返し要素のComponent化
  • レイヤー命名規約（デフォルト名禁止、kebab-case）
  • レスポンシブFrame（PC/SP両方）の存在
  • 画像書き出しマーカー @img-
  • CMS可変領域マーカー @cms-（案件ごとに有効化）
  • アクセシビリティ alt 情報
  • 再現困難パターン（強いブラー、特殊blend-mode）

出力サンプル

$ FIGMA_FILE_KEY=xxx node scripts/check-figma.js --report

Summary: 8 errors, 23 warnings, 0 infos (totalNodes=247)
FAILED ✗

→ 各違反はMarkdownレポートとして出力され、Figma上の該当箇所への直接リンク付き。

設計判断

ルール定義はJSONで外出し。社内事情で閾値や対象を変えられるよう設計しています。Auto Layout の例外条件、許容する色のホワイトリスト、再現困難判定の閾値も rules/check-rules.json だけで調整可能です。

figma-to-spec

目的：Figmaから中間仕様 spec.md の叩き台を自動生成する。Phase 1の主要コンポーネント。

使う人：ディレクター（叩き台を作って、TODOを埋める）。

自動抽出される情報

  • デザイントークン（Color/Text Styles → CSS Custom Properties候補。Enterprise プランは Variables API も併用可）
  • ページ・セクション構成（Frame ツリーから派生）
  • レスポンシブ構成（PC/SP/Tablet Frame の検出）
  • CMS可変領域（@cms- マーカー）と入力タイプの推定
  • 画像書き出し対象リスト（@img- マーカー）
  • アクセシビリティ alt 候補
  • 再現困難パターン警告

人が補完する情報（[TODO]マーカー）

  • 顧客名、業種、ターゲットユーザー
  • 業界制約（薬機法、教育委員会、個人情報など）
  • 検収基準（再現率閾値、Lighthouseスコア）
  • インタラクション仕様
  • 再現困難パターン検出時の対応方針

設計判断

「完全自動」を目指さない。Figmaから取れない情報（顧客背景・業界制約・検収基準）は人が判断すべきもの。このSkillは 「機械的に取れるものは取り尽くす、判断は人に残す」 二段構えで、ディレクターの作業を半分以下に減らします。

Visual Diff Loop

目的：Claude Codeが生成したHTMLと、Figmaの正解画像をピクセル単位で比較し、再現率が閾値を超えるまで自己修正させる。

使う人：Claude Code 自身（自走）／フロントエンジニア（最終確認）。

ループの仕組み

  1. Figmaから正解画像を書き出し（fetch-figma.js）
  2. 生成HTMLをPlaywrightで複数解像度スクショ（render.js）
  3. pixelmatchでピクセル単位比較（visual-diff.js）
  4. JSON＋HTMLレポート生成（差分は赤色で可視化）
  5. 閾値未満なら、Claude Codeが差分画像を読んで該当部分のCSS/HTMLを修正
  6. 再度比較。閾値を超えるか、上限5回まで反復

閾値設計

領域標準閾値備考
全体95%フォントのアンチエイリアス差で1-3%は不可避
重要領域（CTA等）97%個別に厳しく設定可能
装飾領域92%必要に応じて緩める

なぜこれが効くか

従来「人が見て直す」をAIループに組み込むことで、再現率を構造的に上げます。AIに「正解と比較する目」を外付けで与える仕組みです。再現率95%以上が達成できないターゲットは、そもそも上流（Figma側）に問題があるサインなので、構造チェック Skill に立ち戻る判断材料にもなります。

改善ループ — 使うほど賢くなる仕組み

一度きりの設計で終わらせず、案件をこなすたびに精度が上がるサイクルを組み込みます。

なぜこれが必要か

3つのコア仕組み（構造チェック・中間仕様生成・Visual Diffループ）を導入しても、現場で見つかる新しいパターンを反映しないと、ルールがやがて陳腐化します。「気づいた人がたまにメンテする」では続きません。AIに振り返りを書かせ、その蓄積からルール更新を提案させる仕組みを最初から組み込むことで、ワークフロー自体が学習する状態を作ります。

3層のフィードバック設計

Layer 1

振り返りの自動生成

Visual Diff ループ完了直後、Claude Code が retrospective.md の下書きを自動生成。再現率、反復回数、苦戦パターンを構造化記録。

担当: Claude Code（自動） → コーダー（5-10分の補完）

Layer 2

ルール更新提案

蓄積された retrospective を月次集計し、頻出する苦戦パターンを抽出。check-rules.json への変更案を Markdown で生成。

担当: AI（自動） → 管理者が承認

Layer 3

ダッシュボード可視化

案件横断のメトリクスを HTML ダッシュボードで常時可視化。再現率の推移、反復回数の分布、頻出パターンランキングが一目で分かる。

担当: 全社員が閲覧

ループの流れ

振り返りに何が記録されるか

各案件の retrospective.md には、機械的に集約可能な frontmatter として「最終再現率」「反復回数」「業界」「CMS」「苦戦パターンのタグ」が記録されます。自由記述部分には「うまく行ったこと」「苦戦したこと」「教訓」「ルール改善提案」が AI とコーダーの協働で書かれます。さらにコーダー専用の追記欄には「AI が捉えきれない問題」「再現率は出たが本質的に正しくない箇所」「デザイナーへの改善要望」を記録します。

例：3案件後にAIが提案する改善

# ルール更新提案 — 2026-05-31

## 集計サマリー
- 対象案件数: 3
- 平均再現率: 95.7%
- 合格率: 100%

## 頻出する苦戦パターン
| パターン | 件数 | 既存ルールでカバー |
|---|---|---|
| `background-blur-strong` | 2 | ✓ あり |
| `fontWeight-rendering`   | 2 | ✗ なし（要対応） |
| `vertical-rhythm-gap`    | 1 | ✓ あり |

## ルール変更提案

### `hard-to-reproduce`
- 変更: BACKGROUND_BLUR の閾値を radius>20 から radius>15 に下げる
- 理由: 2件で背景ブラーが苦戦パターン化。早期検出が必要。

### (新規) `font-weight-restriction`
- 変更: 新ルール追加
- 理由: フォントウェイト描画差が2件で発生。
  使用可能なウェイトを 400/700 に限定するルールが必要。

運用ルール（重要）

  • 自動承認はしない：AIの提案を直接 check-rules.json に反映させると誤った変更が混入する。必ず人のレビューを経由。
  • 個人評価には使わない：チームの改善が目的。コーダー個人の優劣を測る指標として運用しない。
  • 顧客情報は書かない：retrospective には案件名・業界以上の機密情報を書かない。

期待される効果

導入前後で変わること、変わらないこと。

導入前
  • デザイナーがFigmaを作る → コーダーが受け取り、Figmaの不備に都度気づく
  • Claude Codeに渡しても「だいたい合っている」状態で止まる
  • 人が目視して差分を指摘 → 修正依頼 → 再生成 のループに人が常に介在
  • 再現率は案件・コーダーによって安定しない
  • CMS可変領域の認識が口頭・チャットで揺らぐ
導入後
  • デザイナーが納品前にセルフチェック → エラー0で渡せる
  • 中間仕様(spec.md)で意図を構造化 → AIの解釈ぶれを抑止
  • Visual Diff ループで自己修正 → 人は最終確認のみ
  • 再現率95%以上が標準（重要領域は97%）
  • CMS可変領域がspec.md上で明文化 → バックエンジニアもAIで組込

変わらないこと（誤解の予防）

このワークフローは「人を置き換える」ものではありません。デザイナーの創造性、ディレクターの判断、エンジニアの仕上げの目は引き続き必須です。変わるのは 「人が繰り返し型作業に費やす時間」 であって、判断・創造・最終責任は人が担います。

導入ロードマップ

小さく試して、効果検証してから広げる3ステップです。

Step 1 — Week 1〜2

パイロット案件で試運用

進行中または直近着手予定の LP1案件 + コーポレートサイト1案件 を選定。デザインからコーディング完了までを新フローで実行。

必要なもの: Figma個人アクセストークン、社内検証用GitHubリポジトリ、Claude Code 環境。

Step 2 — Week 3〜4

ルール調整と社内合意

試運用での違反検出傾向を見て check-rules.json を調整。デザイナー・コーダー双方の声を反映してルール完成度を上げる。社内コーディング規約Skillとの境界を整理。

Step 3 — Month 2〜3

全案件への段階展開

まずはLP案件全件 → コーポレートサイト → 学校・医療系の順で展開。各案件で再現率・工数のメトリクスを蓄積。

Step 4 — Month 4〜

営業→制作 連携の改善（次フェーズ）

本提案のスコープ外だが、ヒアリング内容の構造化Skill、見積精度向上の仕組みも続けて整備したい。
